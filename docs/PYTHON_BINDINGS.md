# giant-squid as a Rust library, a CLI and a Python library

This file describes the current design and what is still open. The history
of the work (the plans, the reviews and the decisions as they were made) is
in [`docs/history/PYTHON_BINDINGS_HISTORY.md`](history/PYTHON_BINDINGS_HISTORY.md).
User documentation is in [`README.md`](../README.md), [`PYTHON.md`](PYTHON.md)
and [`V3_MIGRATION.md`](V3_MIGRATION.md); the tests are described in
[`TESTING.md`](TESTING.md).

## Layout

One crate, `mwa_giant_squid`, gives three things. (The crate `xtask`, with its own `Cargo.lock`, has the
maintainer task `cargo xtask regen-openapi`; a plain `cargo build` or `cargo test` does not build it.)

- **The Rust library** (`src/lib.rs`, `src/mwa_asvo/`, `src/helpers/`,
  `src/obs_id/`). It reads no environment variables and prints nothing,
  except `client_config_from_env` and `DownloadSettings::from_env`, which the
  CLI calls.
  - `mwa_asvo/api/openapi.rs`: the types generated by typify from
    `openapi-schema.json` (`cargo xtask regen-openapi`, in `xtask/src/main.rs`).
  - `mwa_asvo/api/client/`: `AsvoClient` (login, the job list, the submissions,
    the cancellation) and the `ENDPOINT_*` paths.
  - `mwa_asvo/api/job_params/`: for each job type, a function that makes the
    request body at the schema's defaults. The CLI and Python set its fields.
  - `mwa_asvo/api/schema_enums/`: the list of the variants of each schema enum
    (`SchemaEnum`, `for_each_schema_enum!`), for the CLI and Python.
  - `mwa_asvo/api/validate/`: the schema's limits, checked before a request.
  - `mwa_asvo/types/`: `AsvoJob` (a checked `JobDetailResponse`), `AsvoJobVec`,
    and the names of `JobState` and `JobType`.
  - `mwa_asvo/download/`: the downloads (keep-tar and stream-untar, resume,
    retries, the hash check, the resume file).
  - `mwa_asvo/env/`, `mwa_asvo/token_store/`, `mwa_asvo/error.rs`.
- **The CLI** (`src/cli/`, feature `bin`): the clap definition
  (`mod.rs`, `params.rs`, `value_enums/`), the command (`run.rs`, `run_cli`),
  the table and `--legacy-json`. `src/bin/giant-squid.rs` only calls
  `run_cli`.
- **The Python module** `mwa_giant_squid` (`src/python/`, feature `python`,
  built by maturin from `pyproject.toml`): a PyO3 wrapper of the library, and
  the private `_run_cli`. The stub is `mwa_giant_squid.pyi`
  (`tools/generate_stubs.sh`). The `giant-squid` command of the Python
  package (`mwa_giant_squid_cli/`) runs the Rust CLI through `_run_cli`.
- **The Python API docs** (`tools/generate_python_docs.sh`, pinned pdoc):
  pdoc documents an importable copy of the stub that
  `tools/generate_python_docs.py` writes, not the built module. PyO3 orders
  the properties of a class by a randomly seeded `HashMap`, so pages made
  from the module change on every run, and pdoc's stub support recurses
  without end on a complex enum (`DownloadProgress.Started.Started` is
  `DownloadProgress.Started`). The copy adds `from __future__ import
  annotations`, drops the enclosing class from the bases of a nested class,
  and gives each enum member its API value from the built module.

CI: `run-tests.yaml` (Rust tests, clippy, the openapi drift check),
`python.yaml` (Python lint, tests, stubtest, the stub drift check, a docs
build, wheels), `python-docs.yaml` (the Python API docs to GitHub Pages, for a
release tag or by hand),
`coverage.yml`, `releases.yaml` (tarballs, wheels, crates.io).

## Design rules in force

- **Every default is the schema's, and `None` is `null`.** The request body
  of each job type starts at the schema's defaults (`mwa_asvo/api/job_params`),
  and the CLI and Python set fields on it. A field that the schema allows to be
  `null` is an `Option`, and `None` is sent as `null`; it never means "use the
  API's default". In Python the default value of each argument of a request
  body class (`DownloadJobParams`, `ConversionJobParams`,
  `ImagingJobFlow1Params`, `ImagingJobFlow2Params`) is made from the schema
  when the class is made, so it cannot drift. Each class also has a
  hand-written `text_signature`, because pyo3 writes only literal defaults in
  a run-time signature and `help()` must show the defaults. Python accepts
  only literals there, so an enum default is its quoted name
  (`'DeliveryDestination.Acacia'`). `tests/python/test_signatures.py` checks
  the text signatures against the schema, and the four classes are in
  `tools/stubtest_allowlist.txt` (the stub has the member, the run-time
  signature the name).
- **Two submit methods, plain request body classes.** `AsvoClient` has one
  method for each MWA ASVO submit endpoint: `submit_download_job` and
  `submit_preprocess_job`. Each request body is a plain, mutable Python class
  (`src/python/job_params.rs`) that holds Python values. It checks the values
  whose Rust type cannot hold a wrong one when they are set (an Obs ID is an
  `ObsId`, and `source_job_id` is not 0), as the library's helper functions
  (`download_params(ObsId)` and so on) do. `validate()` and the submit method
  turn it into the library's request body, which checks the rest, so the
  checks and their messages are the library's. The helper functions of the
  library (`download_params`, `metadata_params`, `voltage_params`,
  `conversion_params`, `imaging_params`, `image_from_job_params`) are in the
  module, and make their class from the library's body. The body of a voltage job
  is a `DownloadJobParams`: the MWA ASVO finds the kind of download from the
  observation, and the module has no check of its own for it.
- **The OpenAPI schema dictates the library.** Defaults, names, limits and
  types come from the schema. Where a schema type exists, the library uses
  it instead of a copy of its own (`JobState`, `JobType`, `JobDetailResponse`
  inside `AsvoJob`, `JobFile`, `JobProduct`, `DeliveryDestination`, `Type`,
  `JobSubmittedResponse`, `JobCancelledResponse`, `Status`). A wrong schema is
  fixed in the API, not worked around in giant-squid. The library may do
  more than the API (for example the downloads).
- **The CLI and Python are thin clients of the library.** They do not repeat
  validation, enums, enum-to-text conversion, request bodies, logic or
  messages. Error messages come from the API and the library unrewritten;
  a change that would rewrite one is the user's decision.
- **Python is a wrapper of the Rust library.** Python class names are the
  schema's (`JobState`, `JobType`, `JobFile`, `JobProduct`,
  `JobCancelledResponse`, `Status`, `Type`) or the library's (`AsvoClient`,
  `AsvoJob`, `AsvoJobVec`). The Python enums are made from the library's list
  (`for_each_schema_enum!`). An argument outside the schema's limits raises
  `AsvoApiErrorInvalidParameter`, the library's `AsvoApiError::InvalidParameter`.
  Every variant of the library's error enums has a Python subclass of the
  enum's exception, named by the two (`AsvoErrorNoAsvoJob`), with the fields
  of the variant, and the variants that wrap an `io::Error` raise `OSError`.
- **The Python API matches the Rust API where possible.** A public item of
  the library (the ones that `src/lib.rs` exports) has a Python item with the
  same name and the same members, and the Python code calls the library, so
  the library's validation, defaults and messages are used and not repeated.
  `tests/python/parity_manifest.py` lists every public Rust item and its
  Python counterpart (`done`, `pending`, `excluded` with a reason, or
  `undecided`); `test_parity.py` checks the list against the module, against
  `src/lib.rs` and against the error enums, so a change on either side fails
  until the list is updated. Python types stand in for the Rust ones where
  needed: `int` for a Job ID or Obs ID, `float` seconds for a `Duration`,
  `datetime.datetime` for a `jiff::Timestamp`, `pathlib.Path` for a `PathBuf`.
- **Names** in the library, the CLI flags, Python and the JSON output follow
  the schema (`job_id`, `obs_id`; `id` in a listed job, as in
  `JobDetailResponse`).
- **Only end-user endpoints** are called, and only fields of the schema are
  sent. The processor and scheduler endpoints are not wrapped (their types
  stay in `openapi.rs`). `staging_count` is never set. The library has no
  unused API calls or fields.
- **`openapi.rs` is committed as `cargo xtask regen-openapi` writes it.**
  `#[rustfmt::skip]` keeps `cargo fmt` off it; do not run `cargo clippy --fix`
  on it. The derives of the generated types are set in `xtask/src/main.rs`.
- **Success or failure is the HTTP status.** `status` of a reply is for
  display. A refused cancel of a job that is already cancelled is HTTP 200
  with `status: failed`; `cancel` never says that a job was cancelled.
- **Strict schema types:** a job state, job type or file type that the
  schema does not list fails the whole listing. A job without a valid Obs ID
  or Job ID is skipped with a warning.
- **`list` without `--days`** uses the schema's default, not the full
  history; `wait` and `download` list jobs the same way.
- **`wait` and `cancel`** take Job IDs only.
- **Downloads:** `--no-resume` downloads again from the start (a complete
  keep-tar file that matches the hash is still skipped); a resumed download
  is always hash checked, even with `--skip-hash`; nothing is written
  outside the download directory (unsafe tar paths, symbolic links). The
  tests that pin these are in TESTING.md, "Tests that pin a decision".
- **`_run_cli`** runs once per process, and not after an `AsvoClient` was
  made (a process has one Rust logger).
- **`--legacy-json`** is deprecated and stays while users need it.
- **Code layout:** a module that has tests is a folder with `mod.rs` and
  `tests.rs`.
- **Process:** one diff per step, from a fresh clone of the latest `apiv2`.
  The user commits and pushes. An existing test is changed only with the
  user's approval.

## Where Python differs from Rust

The Python API matches the Rust API where possible. `tests/python/parity_manifest.py` lists every public item of
`src/lib.rs` and says what Python has for it, or why it has nothing (`excluded`). The differences that are left are
these.

**Types that Python maps.** `Duration` is a `float` of seconds; `jiff::Timestamp` is an aware `datetime`; `PathBuf` is
a `str` or `pathlib.Path` (a `Path` is returned); `AsvoJobId` and the other Job IDs are `int` (not 0); `Vec` is a `list`;
a closure is a callable (`progress` of `DownloadOptions`, `on_result` of `submit_csv_jobs`); a `Result` is an
exception; `ObsId` is a Python class that acts as an `int` where a number is needed (PyO3 cannot extend `int`).

**Items that Python does not have** (`excluded` in the manifest):

- The paths of the endpoints (`ENDPOINT_*`, `API_PREFIX`), `StoredTokens`, the `jiff` re-export, and the
  `validate` helpers that make a schema value from a number (the bindings use them inside).
- `DownloadOptions::should_stop`: a download stops at Ctrl-C (`KeyboardInterrupt`).
- `AsvoJob::is_expired_at`, `display_state_at`, `AsvoJobVec::all_ready_at` (clock helpers for tests) and `retain` (a
  closure; `filter` and list comprehensions do it).
- The variants that wrap an `io::Error` (`AsvoError::IO` and `CannotCreate`, `ParseError::IO` and `StdinIO`,
  `CsvFileError::Read`, `CsvSubmitError::Read`): Python raises `OSError`, with its subclasses.
- `CsvJobParams::endpoint`.

**Items that Python has with a different shape:**

- *Defaults.* A Rust struct has none. Python's `DownloadOptions`, `AsvoClientConfig` (the timeout), `JobsFilter` and
  `CsvDefaults` have the defaults that the CLI has, and `get_jobs`, `parse_manta_ray_csv`, `read_manta_ray_csv` and
  `submit_csv_file` take `None` for a default value of the argument.
- *Request bodies.* A body is a Python class that holds Python numbers (it is the schema's struct and the library's
  helper function in one). The values whose Rust type cannot hold a wrong one are checked when they are set (an
  `ObsId`, a `source_job_id` that is not 0). `image_size` and `nmiter` are newtypes in Rust, but Python checks them in
  `validate()` and when the job is submitted, where the other limits are checked. `PreprocessJobParams` and
  `CsvJobParams` hold the body classes (not copies), so a change to a body after the variant was made is seen when it
  is submitted.
- *`JobsFilter`.* Each value is checked when it is set, as the Rust types do, and `get_jobs` calls `validate()`.
- *`AsvoJobVec::json`.* It does not consume the list.
- *`on_result` of `submit_csv_jobs`.* The Rust loop cannot be stopped, so if the function raises, the other jobs are
  still submitted, it is not called again, and its first exception is raised at the end.
- *Errors.* Every variant is a Python subclass of the enum's exception, named by the two (`AsvoErrorNoAsvoJob`), and
  each also has `kind` and the fields of the variant. `AsvoErrorAsvoApi` is not an `AsvoApiError`: it has it as its
  `source` and `__cause__`, as `AsvoError::AsvoApi` wraps it. `CsvError` and `CsvJobsFailed` have no `kind`.
- *Python only.* `reset_logging`.

## Open items

1. **`dug` for conversion and imaging.** The API developer will add `dug` to
   `ConversionJobParams` and both imaging bodies. When the new schema
   arrives, run `tools/generate_openapi.sh`, and check that the
   `schema_enums` list and the limits tests still pass.
2. **Try a wheel** against the real MWA ASVO and on an older HPC system.
3. **PyPI:** check that `mwa-giant-squid` is free, then publish.
4. **Release 3.0.0:** set the date in `CHANGELOG.md` (still `2026-10-??`),
   tag `v*`; `releases.yaml` builds and publishes. Check `cargo package
   --list` first.
5. **`--legacy-json`:** remove it when the users no longer need it
   (`src/cli/legacy_json.rs`, the options of `list` and `wait`, the README
   and migration text, the tests).
6. **The API developer's changes** (below): regenerate the schema and remove
   the workarounds that each fix makes unnecessary.

## For the API developer

Sent by the user (October 2026), not fixed yet:

- `JobFile.type` uses its own enum `Type`; it should use `DeliveryDestination` (the
  members are the same). Python has `mwa_giant_squid.Type` until then.
- Schema 2.5.0 removed `channel_range`, made `job_id` and `obs_id` typed
  fields of `JobDetailResponse` and made `ImagingJobFlow2Params.obs_id`
  optional (the library leaves it out). Still open:
- Voltage jobs: `delivery` (always scratch) and `delivery_format` (always
  files) are the shared `DeliveryDestination` and `DeliveryFormat` enums, so
  the schema does not show that only one value works. The library does not
  check it: the MWA ASVO refuses any other value for a voltage job.
- `CancelJobParams` should not be a body type of `POST /v2/jobs/create`:
  cancelling is the separate `DELETE /v2/jobs/{job_id}` call (the user told
  the API developer). The client never sends it. No schema sets
  `additionalProperties: false`, and `DownloadJobParams`, `ConversionJobParams`
  and `ImagingJobFlow1Params` need only `obs_id`, so only a live test shows
  that the server tells the remaining body types apart.
- `CalibrationReadyCallback` has `asvo_job_id`.

Not yet raised:

- The schema's paths have no `/api` prefix (for example `/v2/jobs/list`), but
  the API is served at `/api/v2/...`. FastAPI's `root_path` would put the
  prefix in the schema's `servers`; until then the client has it as
  `API_PREFIX`.
- A listed job sometimes has no `modified` key (rather than `null`), and the
  timestamps have no time zone (`2026-09-08T05:41:54.757232`).
  `normalize_job_value` in `src/mwa_asvo/api/client/mod.rs` patches both;
  remove it when the API sends `null` and RFC 3339.
- What do the `error_code` values mean? They are undocumented.
- The `obs_id` minimum of the job bodies is 888888889, but an Obs ID has 10
  digits (giant-squid's `ObsId::MIN` is 1000000000). Should the schema
  minimum be 1000000000?
- `clean_iterations` has a maximum (1000000) but no minimum. giant-squid no
  longer adds a minimum of its own, so a negative value goes to the API.
- Queued jobs have `started` set a few milliseconds after `created`, but the
  field is documented as "when the job began processing".
- The `job_params` of a listed conversion job has `flags: []`, which is not
  a parameter of the request.

Answered:

- `staging_count` was for the processors. Schema 2.3.4 does not have it.
- The HTTP 200 for a refused cancel is only for a job that is already
  cancelled.
- Cancel returns `JobCancelledResponse`.

## Working notes

- Set-up in a fresh sandbox: `apt-get install -y rustc-1.89 cargo-1.89
  python3-dev rust-1.89-clippy rustfmt-1.89`; `export
  PATH=/usr/lib/rust-1.89/bin:$PATH CARGO_HOME=/home/claude/.cargo`;
  `pip install uv`. `uv run` rebuilds the extension when the source changed,
  so `cargo` must be on `PATH` then.
- A command is limited to 300 s: start long builds with `setsid nohup` and
  poll. The disk is small: keep one target directory, and delete
  `target/debug/incremental` when it fills up.
- Checks before a diff: `cargo fmt --check`, `cargo test --locked`,
  `cargo clippy --locked --all-targets -- -D warnings` (also with
  `--features python`), `RUSTDOCFLAGS="-D warnings" cargo doc --no-deps`,
  `uv run ruff check`, `uv run ruff format --check`, `uv run ty check`,
  `uv run pytest`, and `tools/generate_stubs.sh` (the `.pyi` changes only
  when a signature or a docstring in `src/python/` did).
- The README help blocks are the real `--help` output: compare them with the
  built binary when an option changes.
- `tools/run_live_tests.sh` runs the live tests against test-asvo; it needs
  `MWA_ASVO_API_KEY`. The server allows 5 logins a minute.
